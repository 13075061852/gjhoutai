## 一、结论

**当前存在可复现的越权访问、跨账户信息残留和不可信附件同源执行风险；整体应按高风险整改，不能视为“已有登录就安全”。**

直接回答：

- **数据能否被不该访问的人读取？可以。** 已登录的低权限账户可以绕过页面限制，调用业务接口读取共享数据；同一浏览器切换账户后，后一账户能看到前一账户的 AI 分析历史。

优先处理六项：资源级鉴权、旧角色提权、附件安全返回、浏览器账户隔离、上传资源限制、生产运行时与漏洞依赖。

**本次没有修改业务代码、生产配置或业务数据，没有重启/停止服务，没有提交收费 AI 任务。漏洞验证仅使用本机临时数据库、合成账户与合成文件。**

## 三、优先处理的问题

### S01｜高：页面权限没有落实到业务 API

**状态：隔离实测确认；对应后端构建包与生产一致。**

证据：

- `worker/index.ts:84-90`：所有业务部门都有 `state:read`、`state:write`；研发和测试还有 `blob:write`。
- `worker/index.ts:1109-1159`：物性数据读写只检查粗粒度 state/blob 权限。
- `worker/index.ts:1162-1215`：通用状态接口允许访问任意合法公共 key，仅个别特殊键额外受限。
- `src/legacy/features/business-pages/index.ts:1932-1966,5445-5476`：页面查看/编辑权限主要在前端计算。
- `worker/index.ts:984-1078`：检测报告是共享查询，删除不校验创建者，也未结合页面授权。

实测：给销售账户明确设置“办事记录不可查看、不可编辑”后：

| 临时数据上的操作 | 结果 |
|---|---|
| 读取办事记录状态 | HTTP 200 |
| 修改办事记录状态 | HTTP 200 |
| 删除办事记录状态 | HTTP 200 |
| 整体替换物性数据 | HTTP 200 |
| 测试账户删除其他创建者的检测报告 | HTTP 200 |

影响：普通账户、被盗用的普通会话或浏览器内恶意脚本可读取不应开放的业务数据、修改共享记录、删除数据。全局 AI 调用日志也是公共 state，包含问题/回答摘要，不能只靠隐藏日志页面保护。

边界：共享报告是否允许部门内互删应由业务规则决定；本次确定的是“页面无权限仍可调用接口”，而不是认定所有共享读取都应改为私有。

整改：

- 为每个数据集建立服务端资源授权，明确查看、修改、删除、附件维护和共享范围；默认拒绝未登记的 state key。
- 前端和 API 使用同一份权限定义。服务端校验页面/资源覆盖规则，前端只负责呈现。
- 通用 state 接口改为资源白名单；日志按角色/用户最小化返回，不把全局日志默认开放给所有业务账户。
- 共享数据写入增加版本号/If-Match，拒绝旧快照覆盖新数据；对删除保留可恢复版本。

### S02｜高：研发部门的旧 role 会被 AI 项目工具当成系统管理员

**状态：隔离函数实测确认；生产代码一致；当前生产没有研发账户，属于新增/调整账户后可触发的权限缺陷。**

证据：

- `worker/index.ts:76-81`：`研发部 -> system_admin` 的兼容映射。
- `worker/index.ts:563-577,581-609`：创建/更新账户时写入上述旧 role。
- `server/ai/service.mjs:100-122`：AI 鉴权同时取得 role 和 department。
- `server/ai/project-access.mjs:5,28-62`：项目查询、准备及确认启停只检查 `role === 'system_admin'`，没有以 department 为准。

实测：`department=研发部, role=system_admin` 的合成账户通过 `isProjectAdmin()`。

影响：研发账户可能获得原本只属于系统管理员的项目源码读取、项目状态查询及两个白名单站点的启停权限。启停仍需独立确认，但越权用户本人即可执行该确认；这不是一个有效的角色隔离措施。

边界：没有实际启动或停止站点；当前 3 个生产账户中只有系统管理员使用 `system_admin`，没有证据表明此路径已被利用。它不等于任意 root 命令执行，窄代理仍有项目/操作白名单。

整改：统一以明确的服务端权限判断管理员；旧 role 仅用于数据迁移，不参与新授权。覆盖“研发部 + 旧 system_admin 必须拒绝”的回归测试，并检查历史账户的实际字段。

### S03｜高：不可信附件可作为同源 HTML 等活动内容返回

**状态：隔离 HTTP 实测确认返回行为；未执行浏览器脚本，未在线上传测试文件。**

证据：

- `server/ai/service.mjs:40-45`：优先接受客户端给出的非 octet-stream MIME。
- `server/ai/attachments.mjs:35-68`：校验以分类/大小为主，没有拒绝 HTML、SVG 或任意二进制类型。
- `server/ai/service.mjs:265-320`：附件回读沿用记录类型，使用 `Content-Disposition: inline`，无附件级 CSP sandbox。

实测：包含无害脚本标记的合成 HTML 上传成功（201），回读返回：

```text
HTTP 200
Content-Type: text/html
Content-Disposition: inline; filename*=UTF-8''audit.html
Content-Security-Policy: 未设置
正文与上传内容完全一致
```

影响与触发条件：用户上传并在浏览器打开不可信活动文档后，脚本可能在后台站点的 origin 下执行，从而读取其可访问的业务数据、浏览器缓存，管理员场景还可能读取配置接口返回的第三方密钥。`nosniff` 不会阻止明确标为 `text/html` 的文档；HttpOnly 只保护 Cookie 的直接读取，不能阻止携带 Cookie 请求接口。

**附件接口已有 userId 归属校验，不能把此问题描述为“攻击者上传到自己账户后，任意其他账户都能打开”。跨账户利用需要额外的诱导上传/打开等条件。**

整改：

- 默认把所有不可信文档作为 attachment 下载；文本以 `text/plain` 返回。
- 禁止同源 inline HTML/SVG/XML 等活动内容。必要预览放到独立、无后台 Cookie 的文件域，并采用严格 CSP sandbox。
- 图片使用真实格式检测/解码重编码；PDF 校验文件签名，并考虑独立域预览。
- 回归覆盖“客户端伪造 MIME”“HTML 扩展名”“SVG 活动内容”“附件归属”四类场景。

### S04｜高：同一浏览器切换账户后，可看到前一账户 AI 历史

**状态：DOM 隔离实测确认；生产前端 JS 指纹一致。**

证据：

- `src/legacy/features/ai-analysis.ts:25,93-135`：固定使用 `gjh-ai-analysis-sessions-v1`，不含 userId。
- `src/legacy/features/ai-analysis.ts:839-872`：初始化读取上述历史，cleanup 仍持久化该历史。
- `src/services/auth.ts:117-123`、`src/App.tsx:499-506`：退出后清理会话标记/内存并刷新，但不清理本项目敏感持久化内容。

实测：预置账户 A 的合成历史后，以账户 B 初始化实际页面模块，A 的私有标记出现在 B 的分析区域。

影响：公用电脑、交接设备、管理员/员工共用浏览器配置文件时，可能暴露上一个账户的分析内容、问题和工具结果。不依赖攻击者突破服务器鉴权。

扩展风险：图谱 IndexedDB 名称固定为 `gjh-spectrum-images-db`；多项业务缓存及 AI 调用日志也是共享 key，需要按数据分类排查。这里不把所有缓存都认定为私有数据，但当前没有可靠的账户级边界。

整改：私有历史采用 `project:userId:key` 命名或服务端用户隔离；账户切换/退出时清理本项目明确登记的敏感缓存及对象 URL。迁移旧无归属历史时默认不向新账户展示。**不要直接 localStorage.clear()，以免误删同域其他项目数据。**

### S05｜高：上传大小、格式与总量控制不足，可造成数据污染或服务不可用

**状态：部分行为隔离实测，资源耗尽影响为代码/部署配置分析，未压测。**

证据：

- `worker/index.ts:1239-1247`：通用 blob 上传没有应用层实际字节计数限制。
- `worker/index.ts:1147-1156`：备份只检查 Content-Length，缺失该头的流式请求缺少同等限制。
- `worker/index.ts:1012-1019`：PDF 先完整解析 formData，之后才检查文件大小；扩展名为 .pdf 可绕过 MIME 不符。
- `server/lib/r2.mjs:7-19,59-72`：上传先完整缓冲到内存，再写磁盘，并非真正的流式对象存储。
- `server/ai/service.mjs:28,49-59,265-302,372`：上传没有账户存储配额，清理依赖内存 Map；进程重启后旧磁盘附件不在 Map 中，TTL 清理不能自动覆盖它们。
- `server/ai/attachments.mjs:52-59` 定义 maxTotalBytes，但运行入口没有落实该总量限制。
- `server/ai/runtime.mjs:302-315`：新会话先检查运行数，再 await 创建会话，最后才登记 run；并发首请求存在配额检查竞态。本项为代码分析，没有为验证而发起真实模型请求。
- nginx 项目模板单请求上限 120MB；生产两个 Node 服务均 `MemoryMax=infinity`，不能把 nginx 限制等同于安全的并发内存上限。

实测：2,097,153 字节的非 PNG 内容标记为 image/png 后被存入通用 blob（200）；非 PDF 正文仅以 .pdf 文件名上传，被检测报告接口接受（201）。

影响：已登录且有上传权限的账户可能触发大内存分配、磁盘膨胀和无效文件持久化；并发请求会放大影响。公网并非“无限上传”，前置 nginx 有边界，但应用层与账户总量仍不充分。

整改：上传在读取过程中计数，按路由限制实际字节；multipart 在解析前限总请求体；增加文件签名检查、账户/站点配额、上传速率、磁盘水位和 systemd 内存限制。TTL 清理应扫描受控上传目录或依赖持久化索引，避免重启遗留。文件落盘采用临时文件 + 原子替换，失败清理半成品。

## 四、中优先级问题与条件性风险

### S07｜中：登录失败计数存在并发丢失，IP 来源也需可信代理约束

**状态：计数竞态隔离实测确认；IP 风险为配置/代码分析。**

`worker/index.ts:408-427` 使用“先查 failures，再计算，再覆盖”的非原子流程。12 个针对同一合成不存在账户的并发失败请求均返回 401，数据库只记 1 次失败，下一次仍为 401，没有触发 5 次锁定。

这证明请求计数可以丢失；没有用真实账户进行密码爆破，也没有证明可以完全绕过所有防护。

`worker/index.ts:394` 直接信任 cf-connecting-ip 或 X-Forwarded-For 首项；迁移到自托管后应明确谁有权提供这些头。nginx 模板追加 XFF，不能单凭头名认定其不可伪造。即便 IP 维度可绕过，用户名维度仍存在，不能说所有限速都失效。

整改：事务或原子 UPSERT 计数；用户名/IP 双维度加网关节流和告警，限制标识表增长；只信任经过明确代理链清洗的客户端 IP。密码重试、管理操作可增加退避/MFA。

### S08｜中：AI 网关没有统一执行首次改密和页面/资源授权

**状态：首次改密绕过隔离实测；其余为代码确认的授权边界不足。**

`server/ai/service.mjs:100-122` 不读取/检查 must_change_password，后续只要求会话有效。合成的“必须首次改密”账户仍能上传 HTML 附件（201），而主 Worker 对业务接口会拒绝。

`server/ai/tools.mjs:60-225` 的数据库查询工具大多不做页面/资源权限判断，读取只读库并不等于调用者有权查看这些数据。修复主 API 的 S01 时必须同步修复 AI 工具，否则会留下另一条读取路径。

此外，AI 网关拒绝显式恶意 Origin，但对无 Origin 且 Sec-Fetch-Site=cross-site 的合成请求仍放行。这里只确认了策略不一致，**没有证明现代浏览器存在可直接利用的跨站请求链**；主服务已经具备更完整的来源检查。

整改：抽取统一会话安全策略，包括首次改密、激活状态、来源判断、权限、连接撤销；AI 结构化工具在执行时重新验证资源权限，而非只在系统提示词里要求模型遵守。

### S09｜中：主服务和 AI 共用 OS 身份，窄代理的确认边界仅在上层

**状态：生产部署确认；需先发生进程/同 UID 失陷才触发，不是已发现远程代码执行。**

生产两个服务都以 `gjhoutai:gjhoutai` 运行。主代码目录和主入口属于 gjhoutai 且可由该 UID 写入；主服务 `ProtectSystem=full`，不是严格只读代码目录。AI 使用 strict/有限 ReadWritePaths 是优点，但同 UID 不构成完全独立的保密边界。

主配置文件为 root:gjhoutai 640，实测该共享服务 UID 可读，内有数据库配置加密密钥。AI 专用 env 为 root:root 640，该 UID 直接读取被拒绝，不能把两者混为一谈。

`deploy/tools/project-bridge.py:29-38,92`：socket 允许 gjhoutai 组访问，actor/actionId 只校验格式。若同 UID 的主/AI 进程被攻陷，可直接请求固定服务 start/stop，而不经过上层浏览器确认。

边界：窄代理没有 shell，操作和项目仍是固定白名单；未发现任意命令执行，也未调用任何启停操作。

整改：主服务、AI、控制操作服务采用不同最小权限 UID；代码归 root/部署账户所有且运行账户只读；主服务采用 strict + 明确数据写目录。控制服务应验证独立的短期授权/确认凭证，而不是相信任意 socket 客户端声称的 actor/actionId。

### S10｜中：第三方模型、外链图片及运行时 CDN 带来额外外传面

**状态：数据流与渲染代码确认；未进行真实外传或提示注入攻击。**

- AI 上传的图片/文本和业务工具结果会进入外部模型上下文，这是产品数据流，并非“密钥在服务端就没有外传”。需明确配方、客户/项目、检测数据可否发送，以及供应商保留/训练政策。
- `src/utils/aiMarkdown.ts:16-23,79-89` 和 legacy Markdown 允许任意 HTTP(S) 图片地址，渲染会创建 img。若模型受不可信内容诱导，把敏感信息拼入外链图片 URL，浏览器加载可形成外传渠道。禁用 HTML 不能阻断这类 Markdown 外链风险。
- `src/legacy/features/property-analysis.ts:596-637`、`spectrum-analysis.ts:3655-3680` 动态加载 SheetJS/JSZip CDN，无 SRI。第三方脚本在后台 origin 下执行，可使用页面权限读取数据。这里没有证据证明 CDN 已遭篡改。
- `/api/config` 对系统管理员解密返回完整配置；专用功能仍在浏览器中持有第三方密钥。数据库 AES-GCM 加密不能防止管理员浏览器内脚本获取密钥。
- 生产前端 CSP 只有 frame-ancestors/base-uri；AI 路由没有该 CSP，公网响应未见 HSTS。缺少这些加固不是单独的数据泄露证据，但会放大其他问题。
- 项目与根站、/web 共享 origin，后台 Cookie 使用 Path=/、HTTPS 时 SameSite=None。同源其他项目的脚本缺陷可扩大后台风险；Cookie Path 不是跨应用安全边界。

整改：对敏感字段做最小化/脱敏和模型供应商审批；外链图片默认不自动加载，或使用不带用户 Cookie 的受控图片代理并严格防 SSRF；本地打包 CDN 库，或使用固定版本 + SRI；把可复用第三方密钥留在后端调用；评估独立后台/附件子域、严格 CSP、HSTS 和生产仅保留必要 CORS 来源。

### S11｜中：未确认持续、可恢复的业务备份链路

**状态：有限生产检查发现保障缺口；不是断言完全没有备份。**

生产存在 `/var/backups/gjhoutai`，128 个文件约 15MB，其中 2 个名称属于数据库/SQL 类，权限 600；最新文件时间为 2026-10-21。也存在多个代码发布回滚备份。

在已检查的 project timers 和常见 cron 目录中没有找到项目备份任务引用；没有做备份内容读取、异地存储查询或恢复演练，因此不能证明数据库、objects、加密密钥及其版本有完整一致的可恢复副本。外部备份平台或其他命名任务未纳入此次检查。

通用 state 和物性数据写入缺少旧版本，部分直接删除接口会同时删附件；若误删或越权发生，仅有代码备份不足以恢复业务数据。SQLite/R2 适配层未实施应用级业务内容加密，磁盘/备份是否加密尚未确认。

整改：定义 RPO/RTO，采用 SQLite 一致性在线备份，连同对象文件建立版本与关联清单；加密异地备份、密钥单独托管、定期还原验证。不能只复制正在写入的 sqlite 主文件而忽略 WAL。确认旧 Cloudflare D1/R2/Pages 和 OSS 的访问策略、留存及回收计划；不要未经核对就删除回滚资源。

### S12｜中：会话积累和审计能力不足以判断“是否已泄露”

**状态：生产聚合确认；没有判定这些会话恶意。**

生产有 3 个激活账户，57 条会话记录，其中 43 条未到期；默认有效期 7 天，没有发现单账户会话上限或闲置超时策略。多次登录/开发操作可能解释这些数量，**不能据此认定账户被盗**，但会增加遗留会话管理难度。

审计已有成功登录和业务变更，但普通业务读取没有完整的资源/返回量审计；登录失败计数不是完整的失败事件日志。AI 运行中的 SSE/工具不会因撤销会话立即统一断开。当前访问日志中的成功请求不能可靠关联到操作者及读取的数据范围。

整改：限制并展示活跃会话，加入闲置超时、撤销全部会话/设备下线、管理员敏感操作二次验证；为鉴权失败、关键数据导出、批量读取、项目操作记录去敏后的用户/资源/结果/来源；把安全日志发送到独立、不可由业务服务随意改写的存储并设置告警。

## 五、没有发现问题或已有较好防护的方面

这些是本次确认的正面控制，不代表所有路径绝对安全：

- 公网无 Cookie 访问物性数据、配置、AI threads 均返回 401；不存在这三个已检查入口的匿名裸读。
- 主服务与 AI 仅监听 127.0.0.1:8788/8790，没有直接监听公网。
- API SQL 主要为参数绑定；可变表名采用固定白名单。本次未发现可达的直接 SQL 拼接注入入口。
- 会话使用安全随机 token，数据库保存 SHA-256；Cookie 有 HttpOnly/Secure。
- 密码不是明文：使用带随机盐的 PBKDF2；改密/管理员重置会撤销相关其他会话。PBKDF2 100,000 次的工作因子仍可按当前性能/安全基线复核。
- 共享配置采用 AES-GCM，生产加密密钥不是样例占位值；没有在报告或工具摘要输出真实密钥。
- 当前被 Git 跟踪的两个 .env 文件只有前端 API 地址，不是发现了明文凭据；常见密钥模式扫描未确认真实密钥泄露。此类启发式扫描不能证明所有历史都没有秘密。
- 通用状态内部路径、blob namespace、主 API Origin 和 JSON 实际大小已有防护；数据识别历史按 created_by 隔离。
- AI run、上传附件已有 userId 归属校验；正常情况下不能任意读取别人的 run/附件。
- 当前 AI 业务写入默认关闭，历史业务 commit POST 也拒绝，模型没有普通文件/任意 shell 工具。
- root 窄代理使用固定命令数组、项目/扩展名白名单和逐级 NOFOLLOW 路径打开；未发现靠路径穿越直接读取任意系统文件的入口。
- SQLite、对象目录、主配置等生产文件权限总体不是全局可读。数据目录 750，数据库 640，上传目录 700，旧配置备份 600。
- 文档中旧 OSS JSON 地址本次匿名 HEAD 返回 404；这不等于已验证整个 OSS bucket 或旧云环境均安全。

## 六、生产日志抽查：能与不能得出的结论

抽查 nginx 当前及 7 个轮转访问日志，只统计 `/gjhoutai` 请求，没有导出 IP、用户信息或请求正文；同时查看近 7 天三个项目服务的 journald 聚合。

- 日志覆盖到的该项目请求时间约为 2026-10-16 至 2026-10-23；各文件均未触及本次单文件 64MiB 流式读取上限。
- 对 .env/.git、明显脚本/路径探测等有限规则，匹配数为 0。规则不能识别所有攻击，也不检测请求正文中的载荷。
- 近 7 天审计聚合有成功登录 44 次、state.write 1335 次、检测报告新增 20 次、物性写入 10 次等。没有拿业务授权清单逐一确认，不能把这些正常形态操作视为恶意或全部排除。
- 项目窄代理 journald 在已读窗口没有出现 lifecycle_requested/finished 记录，没有证据表明已通过该代理启停站点。
- 主服务有 1 条请求失败标记、AI 有 2 条处理失败标记；没有在已查窗口匹配到 OOM/堆内存耗尽标记。这些错误本身不足以判定入侵。
- 当前账户不处于强制改密状态；当前没有研发部门账户，S02 暂无该部门的现存触发对象。

**结论只能是“本次有限检查未确认既成泄露”，不能升级为“从未被攻击”“数据一定没有外流”。** 如要做正式事件取证，需要更长周期日志、操作者/来源关联、导出记录、会话来源和云平台访问记录。

## 八、整改顺序与验收条件

### 第一批：先收紧可直接访问的数据与权限

1. 落实 S01 的服务端数据集权限，同步覆盖主 API 和 AI 工具；保留业务需要的共享读写，不做未经确认的全局禁用。
2. 修复 S02 的 role/department 混用，在新增研发账户前完成；项目控制能力必要时临时只允许明确管理员。
3. 附件改安全下载/独立域预览，关闭同源活动内容；同时修复 S04 私有历史账户隔离。
4. 上传改实际字节限额、格式校验和配额；为生产进程设合理资源边界。
5. 规划 Node 运行时和 sharp/markdown-it 等依赖升级，测试后再滚动发布。

### 第二批：增强持续保护和可恢复性

6. 原子限速、可信代理 IP、统一首次改密/会话撤销策略、管理员二次验证。
7. 拆分服务 UID、锁定代码只读权限、强化控制代理独立授权；移除生产不必要的 localhost CORS 信任。
8. 敏感数据出站治理、禁默认外链图片、CDN 本地化、严格 CSP 与子域隔离。
9. 建立验证过的异地备份、最小数据留存、账户会话管理及安全日志告警。

### 必须补充的验收测试

- 部门 × 数据集 × GET/PUT/DELETE 的权限矩阵，含“页面被撤权后直接调 API”。
- 研发 department 携带旧管理员 role 时，项目 read/prepare/confirm 均应拒绝。
- A 退出、B 登录，A 的分析正文、工具结果和私有缓存均不能展示给 B。
- HTML/SVG/伪 MIME、伪 PDF、chunked 超限、multipart 超限都安全拒绝或按安全下载返回。
- 并发失败登录准确累计；并发建 AI 会话需先占用配额，不能在异步建会话前检查完就放行全部请求。
- 强制改密、撤销会话后，主 API、AI、SSE 和敏感工具遵循一致策略。
- 真实备份还原到隔离环境，验证数据库与对象文件一致、配置可恢复。

发布时前端、主 Worker 构建包、AI 服务需要按实际修改范围一起更新；只改页面不能修复后端越权。整改后再做一次隔离复验与生产无损检查。
